How I measure a model on a broken React controller

This eval does not ask a model to build a feature. It hands over a working app with four production incidents in it and asks for the repair — then scores whether the fix has real ownership boundaries or is just a controller that got longer. This page is the method, not a ranking.

Task13-support-inbox
Judgegpt-5.6-sol · codex · medium
Rubric6 dimensions · 18 criteria
Hidden traces11
Cost per run$0.24 – $3.50 all-in
STEP 1

A model inherits a 189-line React controller that works in ordinary use and a brief describing four incidents in operator language — no mechanism names, no file names.

STEP 2

The harness records the gates — typecheck, lint, supplied tests, production build — then runs eleven hidden Vitest traces the model never sees.

STEP 3

A blinded judge gets only the diff, the gate results and the named trace outcomes. No model name, no other submission, no ranking.

STEP 4

The judge fills a worksheet: every criterion scored 5 / 2.5 / 0, a deduction ledger so one root cause is charged exactly once, and a file:line for every point withheld.

Inside each dimension

Criterion by criterion

Every criterion in D2–D6 is worth 5 points and scores strong 5 · mixed 2.5 · weak 0. Mixed is for a localised limitation with no demonstrated invariant violation — the rubric says explicitly that it is not a default for criteria with several clauses.

D2

React state and lifecycle ownership

max 20

The inherited controller keeps four mutable refs alongside eight pieces of React state. The question is not whether the repair still works — it is whether anything still has to be manually kept in sync.

#CriterionPoints
D2.1Values the view can derive — the selected ticket, its pending status, which feedback is visible — are computed at render rather than stored in state and kept up to date. Derived-versus-stored only; a duplicated owner of the same value is D2.25 · 2.5 · 0
D2.2Mutable refs and React state do not form competing mirrors that require unrelated callbacks to keep them in step5 · 2.5 · 0
D2.3Effects and external subscriptions express one synchronisation purpose, with complete dependencies and symmetric cleanup5 · 2.5 · 0
D2.4Strict Mode replay, unmount and remount cannot duplicate durable effects, skip the first useful request, or leave disposed work able to publish5 · 2.5 · 0
D3

Search and navigation resilience

max 25

The deterministic API is built so that completion order is observable without a network: some queries cross a cancellation boundary before they settle, so aborting them changes nothing. A repair that only calls abort() cannot pass D3.1.

#CriterionPoints
D3.1The newest intent exclusively owns results, errors and loading completion; superseded work cannot publish, including requests already past the cancellation boundary5 · 2.5 · 0
D3.2Retry belongs to the intent that produced the error; a later control or navigation change revokes it rather than replaying stale criteria5 · 2.5 · 0
D3.3Existing results and the open conversation stay usable while replacement work waits or fails; the ordinary loading, empty, error and Retry flows still behave as supplied5 · 2.5 · 0
D3.4URL initialisation and later writes normalise owned values, reflect current controls immediately, and preserve unrelated parameters5 · 2.5 · 0
D3.5History records only operator selection as a new entry; control changes and automatic fallback replace it, and Back/Forward restore intent without loops, duplicates or stale pre-navigation publication5 · 2.5 · 0
D4

Optimistic mutation consistency

max 20

Status changes have ticket-specific latency and one deterministic failure. The inherited controller blocks all mutations while any one is in flight and keeps a single feedback object, so notices attach to whichever ticket is selected.

#CriterionPoints
D4.1List and detail share one immediate optimistic value; failure restores the exact owned snapshot and success reconciles the server ticket5 · 2.5 · 0
D4.2Pending state and progress, success or failure feedback are owned per ticket and survive selection changes5 · 2.5 · 0
D4.3A repeated change to a ticket with an update in flight starts no second request, while different tickets settle independently without overwriting one another5 · 2.5 · 0
D4.4Search snapshots and mutation outcomes compose in either completion order without erasing pending or already confirmed values5 · 2.5 · 0
D5

Feature architecture and maintainability

max 20

The only dimension where passing every trace earns nothing. The rubric states it directly: full D5 credit requires genuinely separated ownership boundaries; working behaviour alone is insufficient.

#CriterionPoints
D5.1Location parsing, normalisation, history writes and the popstate subscription form one focused boundary rather than browser mutations scattered across effects5 · 2.5 · 0
D5.2Search scheduling, invalidation and publication policy have one reviewable transaction boundary rather than duplicated promise branches and incidental refs5 · 2.5 · 0
D5.3Optimistic overlay, rollback, reconciliation and feedback policy have one ticket-keyed boundary rather than singleton or callback-local ownership5 · 2.5 · 0
D5.4Given whatever boundaries the repair established, the composition layer itself is sound: no pass-through wrappers, dead indirection or speculative machinery, and names that state the invariants. Never charge a missing boundary here — that is D5.1–D5.35 · 2.5 · 0
Scoring D5.1–D5.3 — a three-step ladder, not a yes/no
5

The concern is extracted and owns its state. A reader changes it in one place.

2.5

Partly extracted: named module-level helpers exist and centralise part of the concern, but ownership still leaks back through refs, effects or callbacks.

0

Still inline, with no extraction beyond incidental local functions.

A generic utility carrying no policy — an abort-error predicate, a parameter setter used once — is incidental and does not on its own lift a criterion to 2.5. This ladder is the whole difference between the v3 and v4 rubrics, and the reason D5 grades degree rather than counting files.

Generality check — mechanical. The judge greps the diff for the supplied fixture literals ('billing', 'invoice', 'timeout', 'offline', any TKT- id) and for latency constants copied out of the API (520, 220, 120, 240, 80). Control flow branching on any of them is a fixture-specific patch, not a repair: the boundary criterion it sits in scores 0. No submission has tripped it so far.

The eleven hidden traces

And which criterion owns each

Naming the owner of every trace in the rubric is what stops the same failure being re-attributed to a different dimension on a re-run. A failed trace forces its criterion to 0, not mixed. A passing trace is not automatically full credit — a source-level counterexample still forces 0, and some of the largest deductions on record come from defects no trace caught.

How many runs a number needs

Reading the noise

A single run does not produce a usable score. Models re-run on the identical task write materially different repairs, so the method has to say how many attempts a published figure rests on — and at what reasoning effort.

EffortRunsScoresMedianSpread

One model, twelve runs, same task. Raising reasoning effort lifts the median 15 points and saturates at high. All four bands cost between $0.24 and $0.28 per run all-in, so the setting is close to free — which is exactly why it has to be fixed and disclosed rather than left to whatever was convenient.

A different model at fixed effort. Run 3 genuinely broke two production invariants — the spread is the model being inconsistent, not the judge. Published as a single run this model ranks anywhere from first to eleventh.

Careful

A stable total is not a stable submission

The three high runs above all scored 77.5 — by completely different routes. One earned a perfect D3 with a monolithic controller; another shipped three modules and a broken search; the third sat between them. They converge on one total through compensating differences, not by writing the same repair.

So the honest claim is that raising effort lifts the median and tightens the total. It is not evidence that the model became deterministic.

Method

What gets published

Three runs per model at one fixed reasoning effort, reported as the median with the spread shown. Effort is held constant across every model, because on the ladder above it is worth ~15 points — three times the gap that currently separates the strongest models from each other.

Scoring is absolute: each submission is judged against the rubric alone, never against another submission, and the judge never sees a model name.

When a run doesn't count

Before scoring begins

A submission is only judged if it clears these first. Nothing here is a scored zero — the run is discarded and re-run, so a harness or provider problem never lands on a model's record.

Rejected asWhat happened
path violationThe diff touched a file outside the two permitted paths — in one case a jsdom-debug.mjs the model left at the workspace root. The allow-list is what keeps a repair from quietly editing the tests or the API.
no changesThe agent finished without modifying a candidate file. Usually a model that spent its whole budget reading and planning.
boundary violationThe transcript shows the agent reaching for the hidden tests or the evaluator directory. Exclusion patterns don't count — a model that tells ripgrep to skip .eval-tests is obeying the boundary, not crossing it.
timeout / lengthThe wall-clock limit expired, or the model exhausted its context. Wall-clock is the only budget, and it is identical for every agent.
